# EP-TTA v0.1.0：R5 第二阶段后续方案

日期：2026-09-17  
性质：供编码 AI 执行的建议方案与工单，不是本次远程执行结果。  
起点：用户报告 AASIST R5 第一阶段已 PASS；全量缓存与源资源尚未执行。

## 1. 现在要完成的闭环

**全量源缓存 → 独立重编码 parity → U / tau0 / M → 依赖闭合的 Fisher / static R → 真实资源重载验收。**

不重新训练 AASIST、不操作 SSL、不重划数据、不重做整轮 R4 和小缓存。
`K=0` 通过只证明无更新接线，不证明真实 `K>0` 更新或检测收益。

## 2. 数据与依赖

| fit | 25,380 | 缓存、U、M、合同允许的 Fisher / source-only 对照 |


“static R 需要源选择”的含义尚不能仅凭当前报告确定。

由执行 AI 从项目代码和合同展开。缺失定义须在 proposal 中明确，不代为发明。

## 3. 全量缓存不是把小缓存改个名字

保持 `[identity, deterministic_noise, deterministic_fir]`、seed13、
16kHz / 64600 samples、FP32、block_units=256 和原实际 probe 参数。
每角色新建不可覆盖全量 cache identity。

单流按 256 条连续分块时：
- fit：99 个完整块 + 36 条尾块，共100块。
- cal0：19 个完整块 + 42 条尾块，共20块。
- select：45 个完整块，无尾块。
存在多分片时应解释真实布局，不硬凑该块数；UID 覆盖仍须恰好一次。

建议固定生产 batch 做全量 extract 一次、独立重编码 parity 一次。
真实块边界另外用小清单检查，不对全量数据重复所有 batch 组合。
保持既定联合容差，FP32 无损落盘 roundtrip 单独要求逐位一致。
K=0 复用已有入口检查，不新增另一条绕过生产逻辑的路径。

## 5. 建议预算与批准

根据用户报告外推，全量提取约0.116 GPUh，加一次同规模 parity 约0.23 GPUh；
这不是本次全量实测，更不包括所有资源拟合的不确定开销。

建议第二阶段申请：
- 新增单卡累计上限 **1.0 GPUh**，含失败、重试及源拟合占卡时间；
- 新增工件峰值上限 **2.0 GiB**，含临时副本；
- CPU/bootstrap/静态优化按新 proposal 固定规模与迭代上限，实测计量。

这是资源上限，不是运行时长承诺。不自动沿用阶段一剩余预算。
新 proposal 一次覆盖全阶段，只在首次真实执行前按合同批准一次。
不得对 fit/cal0/select/U/tau0/M 分别重复索要已有授权。

## 6. 成功交付的内容

三角色全量缓存均有精确覆盖、可信 identity 与独立 parity；
U 满足预定正交/秩/能量/稳定性检查；
tau0 按 cal0 的既定分位数口径固定；
M 仅来自 fit，实际满足固定阈值与分层要求；
依赖闭合的 Fisher/static 真实拟合，其余项明确记录待办；
生产 loader 能加载这些真实工件，并拒绝错误角色、hash、维度和血缘。

不要把“资源能构建”写成“EP 有效”，或据此宣称支持 H1–H7。
资源冻结也不等于 R7 的完整方法与确认性实验计划封存。

## 7. 下一轮才是 R6

R5 之后优先：
真实 K=1 小规模更新/梯度/reset 检查；
随后在源 select 上比较 Frozen、同视图平均不更新、完整 EP、
既有 P0/P1/static/scalar/subspace 与关键消融。
输出检测效果、按类有益/有害翻转、失败回退和完整成本。
R6 的具体方法、候选范围和数据条件由实际 DESIGN/registry 固化，
不因旧对话建议就自动新增 noise20/band8 或九点搜索。

此时仍不查看四个目标测试效果，不因为某个对照待实现就无限延后核心 EP 先导。
但不能跳过实际 EP 入口所需的资源资格门禁。

## 8. 本执行包怎么使用

先把 `01_SEND_TO_AI.txt` 交给项目内编码 AI。
它应先完成必要代码与 CPU 检查，输出新 proposal 完整 hash。
使用 `02_APPROVAL_TEMPLATE.txt` 审阅后批准，再在该范围内连续执行。

本执行包自身的任何文件 hash 均不是远程运行 proposal 的批准 hash。
